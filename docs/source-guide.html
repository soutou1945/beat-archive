1. 全体像

React 19、TypeScript、Viteで構成された単一ページアプリです。取込ファイルはブラウザで解析され、Supabase設定時はログインユーザー専用の行として同期されます。未設定時はブラウザの保存領域へ退避します。

入力ファイル → パーサー → Snapshot → Store → 集計・推薦 → React UI

全ゲームの取込履歴は共通のSnapshot型へ変換されるため、表示側はゲームごとの差を限定したまま、最新値と前回値を比較できます。

3. データフロー

  1. 取込: ユーザーがCSVまたはCHUNITHM JSONを選択します。
  2. 解析: CSVはparseCsvSnapshot系、JSONはmakeChunithmSnapshotで検証されます。
  3. 正規化: ゲーム固有データを共通のSnapshotへまとめ、取込日時とファイル名を付与します。
  4. 永続化: saveSnapshotがSupabaseまたはブラウザ保存を選択します。
  5. 比較: 最新と一つ前のSnapshotから推移や更新量を算出します。
  6. 表示: ゲーム別ダッシュボードが集計表、グラフ、推薦を描画します。
重要: パーサーは外部入力との境界です。型アサーションだけに頼らず、必須値・数値範囲・ゲーム識別子を実行時にも検証します。

4. CHUNITHM関連コード

4.1 取得ツール

public/chunithm-exporter.jsはCHUNITHM-NETと同じオリジン上で実行します。プレイヤー情報、BASIC〜ULTIMAの難易度別一覧、ベスト枠、新曲枠、候補枠を順番に取得します。リクエストにはログイン中のCookieを利用しますが、JSONへCookieや認証情報は格納しません。

HTMLの揺れに備え、曲名・レベル・スコアは複数セレクターから探索します。各譜面のIDは公式のidxと難易度を優先し、得られない場合は曲名と難易度を使用します。巡回途中の結果は同じIDでマージされ、レーティング枠情報が難易度一覧の値へ追加されます。

4.2 JSON契約

{
  "schema": "beat-archive.chunithm.v1",
  "exportedAt": "ISO 8601 date",
  "playerRating": 12.34,
  "scores": [{
    "id": "music-id::MASTER",
    "title": "曲名",
    "difficulty": "MASTER",
    "level": "14+",
    "score": 1007500,
    "rank": "SSS",
    "clear": "CLEAR",
    "isNewSong": false,
    "frame": "best"
  }]
}

src/chunithm.tsはschema、配列、難易度、曲名、レベル、スコア範囲、プレイヤーレートを検証します。同一IDは最後の項目を採用します。ランク表示は入力文字列ではなくスコア閾値から再計算でき、集計の一貫性を保ちます。

4.3 推薦

ベスト枠と新曲枠を分離し、次のランクまでの距離、前回からの伸び、レベルを加味して候補を並べます。MAX到達済みと未プレイは除外し、上位10件を表示します。

4.4 障害調査

  • 「ログインが切れています」: CHUNITHM-NETへ再ログインしてから再実行します。
  • 「楽曲一覧を検出できません」: 公式HTMLのclass名やURL変更を確認し、パーサーとfixtureテストを同時に更新します。
  • 一部未取得: 表示された対象名を確認します。成功分は保持されるため、通信状態を整えて再実行できます。
  • 枠が空: rating detailページのform構造と、各項目の難易度推定を確認します。

5. SDVX / IIDX

src/csv.tsがヘッダーからゲームを判定し、表記揺れを吸収します。SDVXはスコア・EXスコア・クリアランク・グレードを取り込み、src/vf.tsで譜面別VFを算出します。IIDXはANOTHER / LEGGENDARIAを対象としてEXスコア、ミスカウント、クリアランプを保持します。

CSV仕様が変わった場合は、ヘッダー別名、列インデックス、数値変換の順で確認し、匿名化した最小入力をテストへ追加してください。

6. 保存と同期

src/store.tsは環境変数VITE_SUPABASE_URLとVITE_SUPABASE_ANON_KEYが揃う場合だけSupabaseクライアントを有効化します。ログイン時はスナップショットをユーザーIDに紐付け、RLSにより本人だけが操作できます。

Supabase未設定時のブラウザ保存は開発・試用向けです。ブラウザデータ削除や端末変更では失われるため、継続運用ではSupabaseを設定します。CHUNITHM-NETのログインCookieはBEAT ARCHIVEへ渡りません。

7. 画面構成

src/App.tsxがゲーム、検索条件、取込中状態、認証状態を保持します。純粋な計算は各ドメインモジュールへ委譲し、src/components.tsxは受け取った値を描画します。見た目はsrc/styles.cssへ集約され、モバイル幅を基準に調整されています。

新しい表示を追加するときは、まず純粋関数として計算とテストを作り、その結果をpropsでコンポーネントへ渡すと、画面とロジックを独立して保守できます。

8. データベース

score_snapshotsはユーザー、ゲーム、取込日時、ファイル名、JSON payloadを保持します。新規構築はsupabase/schema.sqlを一括実行し、既存のSDVX / IIDX環境はsupabase/chunithm_migration.sqlを適用します。

ゲーム追加時はTypeScriptのunion型、取込処理、UIだけでなく、データベースのgame制約も必ず更新してください。RLSを無効化した状態で公開しないでください。

9. 開発・テスト

pnpm install
pnpm dev
pnpm test
pnpm build

pnpm testはVitestの単体テスト、pnpm buildはTypeScriptの型検査とViteの本番生成を実行します。Windowsでは同梱のpnpm.cmdも利用できます。

環境値は.env.localに置き、Gitへ登録しません。anon keyは公開クライアント用ですが、データの分離は必ずRLSで保証します。

10. 変更時の確認項目

  • 外部入力に空値、重複、不正な数値、未知の難易度があっても明確に処理されるか。
  • CHUNITHMの公式ページ変更時、一覧・レーティング枠・プレイヤーレートを個別に確認したか。
  • 最新履歴だけでなく、前回履歴との比較結果が正しいか。
  • Supabase有効・無効の両方で、保存と再読込が成立するか。
  • スマートフォン幅、長い曲名、データ0件、通信失敗を確認したか。
  • pnpm testとpnpm buildが成功したか。
  • 仕様変更をREADMEとこの説明書へ反映したか。
